# Should Orchestraitor adopt `rig` (0xPlaygrounds) as its provider/LLM dependency?

**Eval date:** 2026-10-13 · **Rig evaluated:** v0.44.0 (released 2026-10-07, commit `9e7cb60` on main)
**Local ground truth:** `AGENTS.md`, `docs/spec/tech-stack.md`, `docs/spec/30-model-routing.md`, `crates/orchestraitor-provider-api/`

## 1. What rig is

Rig is an opinionated Rust framework for building LLM applications: ~25–30 provider adapter
wires (rig `crates/rig-core/src/providers/` — openai, anthropic, gemini, bedrock,
vertex, zai, deepseek, openrouter, …), an agent abstraction with a tool-calling loop
(`rig-agent`), RAG/vector-store integrations (~18 optional crates: lancedb, qdrant, sqlite,
mongodb, …), streaming with live tool-argument deltas, typed generation options, and a
built-in model catalog (1,492 rows / 28 vendors, models.dev-derived — rig CHANGELOG 0.44.0).

Maintenance signals (verified 2026-10-13):

- **License:** MIT (repo LICENSE, root `Cargo.toml` `license = "MIT"`, GitHub API). Passes the allowlist.
- **MSRV:** `rust-version = "1.95.0"` (workspace, `Cargo.toml:218`); toolchain 1.95.0. Orchestraitor pins 1.96.0 (`rust-toolchain.toml`) → **no conflict**.
- **Cadence:** 10 releases Jun–Oct 2026 (0.37.1→0.44.0, `CHANGELOG.md`); last push 2026-10-13. 8,868 stars, 113 open issues, active org.
- **Churn:** 171 `**breaking**` markers across those 10 releases (~17/release); 0.x semver so minor bumps routinely break.
- **unsafe:** zero `unsafe` blocks in `rig-core`, `rig-http`, `rig-agent` source (grep; only a test *name* contains the word). Clippy lints mirror ours (`deny(unwrap_used, expect_used, panic)`).

## 2. Pros of adopting

- **Provider breadth for free:** rig-core carries ~25–30 maintained wires, incl. `zai` and
  `deepseek` — the same families that motivated pinning genai (tech-stack.md:282).
- **Modern streaming semantics:** 0.44 streams tool-call argument fragments as they arrive
  (`StreamEvent::Arguments`, `parse_partial_arguments` — CHANGELOG 0.44.0); typed
  `GenerationOptions` incl. `reasoning` with per-provider `UnsupportedOption` refusal policy —
  a more rigorous shape than our free-form `ModelRequest.extensions` map
  (`provider-api/src/transport.rs:79`).
- **Quality floor is real:** workspace lints deny unwrap/expect/panic; cassette-based test
  infra (`rig-cassette`) is a mature pattern adjacent to our testkit simulator.
- **License/MSRV/deny gates pass** (verified below), so adoption is *permitted* — the case
  against is architectural, not compliance.

## 3. Cons

1. **It duplicates the layer we deliberately own.** `ProviderTransport`
   (`provider-api/src/transport.rs:18` — `descriptor/list_models/stream/count_tokens/health`)
   and `AgentAdapter` (`adapter-api/src/lib.rs:25`) are the mandated isolation seams
   (AGENTS.md: "isolate third-party crates behind project-owned traits"). Rig's value is
   concentrated *above* the wire — agent loop, tool loop, RAG, catalog, cost — and every one
   of those layers is one Orchestraitor already builds or must control:
   - **Agent/tool loop:** rig's `Agent` would compete with `orchestraitor-worker`'s call loop
     (`worker/src/model.rs::call_model`: bounded retries, event folding, usage accrual, daily
     spend soft-cap) and its four-tool mediated executor. Spec 30 §9.19/§9.45 requires every
     call to produce routing decision records, Arbitraitor receipts, and ledger entries; rig's
     loop has no hook seam for any of that. We could not use it without forking it.
   - **Model catalog:** rig's `rig_core::catalog` (1,492 models.dev rows, CHANGELOG 0.44.0)
     collides head-on with `orchestraitor-provider-meta` ("Live-first models.dev metadata
     client with cached and bundled fallback", `provider-meta/src/lib.rs:1`) — a second,
     un-governable copy of capability metadata that spec 30 §9.29 requires be
     source/confidence-provenanced.
   - **Cost:** rig 0.44 auto-fills `Usage::cost` in USD from provider figure *or catalog list
     price* (CHANGELOG 0.44.0). Spec 30 §9.19.4 splits API spend vs subscription utilization
     and forbids inventing monetary cost for flat-rate subscriptions. Rig's cost model
     actively fights the ledger's `monetary_cost_{measured,estimated,basis}` governance.
2. **What we'd actually consume is only the wire layer — which genai already covers.** Behind
   `ProviderTransport`, rig-core degenerates to "another set of provider HTTP wires", the same
   slice genai 0.6.5 is pinned for (workspace `Cargo.toml:178`), with escape hatches already
   designated for native gaps (`async-openai`, `claude-api`, `gemini-rust` — tech-stack.md:175).
   Rig adds RAG/vector stores we will never adopt (Arbitraitor-mediated memory is in-house,
   tech-stack.md §14 `orchestraitor-memory`).
3. **Dependency weight:** a minimal rig-core (default-features off, `derive+reqwest+rustls`)
   resolves to **~150 unique crates** (measured: scratch `cargo tree`, 143 normal-edge deps /
   154 incl. build). License scan of the resolved tree passes our `deny.toml` allowlist
   (only pre-approved expressions: MIT/Apache/BSD/ISC/Unicode-3.0/CDLA-Permissive-2.0/Zlib;
   `ring` covered by the existing clarify block) — but the audit/vet surface roughly doubles
   versus genai's more modest tree, for the same capability.
4. **Breaking-change churn:** 0.x with ~17 breaking changes per release (171 across 10
   releases). Exact-minor pinning policy (AGENTS.md) means a migration PR nearly every bump.
   tech-stack.md:291 **already rejected `rig-core 0.40.0`** on exactly this basis
   ("Here be dragons… breaking changes"); 0.44.0 does not change that character — the
   CHANGELOG shows three `[breaking]` core changes in 0.44.0 alone.
5. **Boundary type friction:** our `ModelEventStream` is a boxed *sync* `Iterator`
   (`transport.rs:14`) and `ModelMessage` is text-only (role + `String`, `transport.rs:57`);
   rig is futures-`Stream`-based with rich typed messages (thinking blocks, citations,
   images). Interleaved thinking (spec 30 §9.29 adapter knowledge, GLM-5.2) cannot cross our
   current trait shape with *either* library — but adopting rig doesn't fix that either; the
   adapter conversion layer is the same work as for genai.
6. **Lock-in posture:** rig is a single-org framework with an opinionated facade (`rig` crate
   re-exporting everything); its release-plz-driven cadence means its API surface moves at the
   maintainers' pace, not ours. Behind our traits the exit cost is low, but so is the retained
   value.

## 4. Comparison vs genai (incumbent)

| Dimension | genai 0.6.5 (pinned, workspace Cargo.toml:178) | rig 0.44.0 |
|---|---|---|
| License | MIT OR Apache-2.0 ✅ | MIT ✅ |
| MSRV vs 1.96 pin | compatible | 1.95.0 ✅ compatible |
| Providers | 30+ incl. zai, bigmodel, moonshot, vertex, bedrock, copilot (tech-stack.md:282) | ~25–30 incl. zai, deepseek, openrouter |
| Agent/tool/RAG layer | none (transport only — fits our seam) | full framework (unused/contremps behind our traits) |
| Model catalog / cost | none (we own provider-meta + cost-ledger) | built-in catalog + USD cost — **conflicts** with spec 30 §9.19.4/§9.29 governance |
| Breaking churn | 0.x; 0.7.0-beta in flight, deliberately NOT pinned (tech-stack.md:282) | 0.x; ~17 breaking/release (worse) |
| Known wart | name-prefix adapter inference + convenience fallbacks — spec 30 (~line 597) demands explicit adapter forcing | typed option refusal policy is cleaner |
| unsafe / deny gates | pass | pass (tree scan) |

Note: today **no crate code calls genai**; the one wired transport is a hand-written reqwest
adapter (`provider-neuralwatt/src/transport.rs`). genai is the spec-pinned baseline, not yet
load-bearing — which is exactly why a second framework adds no urgency.

## 5. Verdict: **Reject (maintain the existing rejection)**

tech-stack.md §4.4 already lists `rig-core` as rejected; this evaluation confirms that ruling
against the current 0.44.0. Reasoning tied to this repo's constraints:

- The compliance gates (license, MSRV, cargo-deny, unsafe) all **pass** — the disqualifier is
  that rig's differentiating layers (agent loop, catalog, cost, RAG) are precisely the layers
  spec 30 and AGENTS.md assign to project-owned, Arbitraitor-mediated code. Behind
  `ProviderTransport` we'd retain only the HTTP wires, a slice genai already occupies at lower
  dependency weight and comparable provider coverage, with designated native escape hatches
  for gaps.
- Migration cost is negative-value: an adapter rig→`ModelEvent`/`ModelRequest` conversion
  layer, a second models.dev catalog to reconcile with `provider-meta`, and a recurring
  breakage tax against an exact-pinning policy.
- Genai comparison offers no decisive rig win; the one genuine rig nicety (typed generation
  options with per-provider refusal) can be ported into our own `ModelRequest.reasoning` /
  `extensions` evolution without the dependency.

**Trigger to revisit ("adopt later"):** only if (a) rig reaches a semver-stable 1.x with a
measurably lower breaking-change rate, AND (b) a concrete provider feature needed by spec 30
(e.g. interleaved-thinking or reasoning-effort surface on a provider genai and both escape
hatches lack) is demonstrated in rig first. Even then, adopt **rig-core wires only** behind
`ProviderTransport`, feature-gated like the existing escape hatches — never `rig-agent`,
catalog, or cost layers. [INFERENCE on 1.x timing: no published 1.0 roadmap was found.]
